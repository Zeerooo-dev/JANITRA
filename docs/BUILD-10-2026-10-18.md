## Setup codes

An issued setup/recovery code keeps its existing 30-minute expiry when the issuing Supervisor signs out. Redemption and completion still recheck the issuing Supervisor's active profile and current authority over the person's workplace scope. Suspended/revoked issuers, expired/replaced/consumed grants and mismatched account identifiers remain denied. Issuance still requires a current Supervisor session, password confirmation and configured MFA. Code expiry is never extended by signing out, claiming or retrying.

For an email-invited Personnel account that has not completed invitation setup, a valid Supervisor-issued handoff claim can authorize Auth email activation together with the chosen password. Only the server's validated claim can request this; a client cannot choose the target or request email confirmation. This is Supervisor-authorized account activation through the one-time credential, not proof that a mailbox was accessed. Already-confirmed and username accounts keep their existing behavior. Failed/ambiguous Auth completion retains the existing fail-closed rules.

## Owner permission and permanent deletion

The user explicitly selected existing `jeffirie12@gmail.com` as owner, chose permanent erasure of related history over anonymized retention, and approved deploying both migrations/functions plus that permission. Exactly one private owner permission is configured. The application still has only Supervisor and Personnel workplace roles. No new account or password was created.

Sign in as that owner and refresh Team. Open a person's menu, select **Delete account permanently**, read the erasure description, type `DELETE`, and confirm the owner's password/MFA. Both Personnel and Supervisors can be targets. Owner accounts, including the current owner, are protected from deletion to prevent lockout. Ordinary Supervisors receive no deletion control or backend capability.

The existing `manage-users` endpoint verifies the live owner and password/MFA, prepares a two-minute deletion approval bound to actor, original session and target, then calls Supabase Auth's administrative deletion API. A private BEFORE DELETE trigger rechecks that authorization and removes related application rows in the same database transaction as Auth deletion. Unexpected constraints roll the operation back. The history-delete exception is limited to that private running transaction; clients cannot enable it with metadata, SQL settings or table grants. No table triggers or RLS policies are disabled.

Erasure includes profile, assignments, own PIN credentials, identity mapping/grants, own schedules, linked tasks/submissions/reviews/notifications, exports, receipts and related application audit/security history. Deleting a Supervisor can erase shared task/review records involving them, as stated in the confirmation dialog. Other Personnel accounts and their usable PINs remain; creator/credential custodian references move to the owner where needed. Shared agencies, clients and workplaces remain. Provider-managed logs, existing backups, already-exported files and disconnected devices are outside this live database erasure. There is no undo button.
